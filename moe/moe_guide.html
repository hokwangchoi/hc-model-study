Mixture-of-Experts LLMs

Most frontier open LLMs are now sparse: hundreds of experts stored, a handful used per token. This guide covers the router, the MoE decoder block, the latent-attention KV cache that usually comes with it, and what all of this means for memory, bandwidth and GPU kernels at inference time.

Prerequisites

  • Why autoregressive decode is memory-bandwidth-bound (covered in the transformer guide's memory analysis).
  • Helpful: Module 5: Mamba, the other route to cheap long-context inference.

The Core Idea: Conditional Compute

Intuition first. An MoE layer is a team of specialists with a dispatcher. The dispatcher (the router) reads each token and sends it to the two or eight specialists best suited to it; everyone else on the team sits idle for that token. You pay to keep the whole team on staff (memory), but each token only pays for the few it talks to (compute and bandwidth).

In a dense transformer, every token goes through every weight. In a sparse Mixture-of-Experts (MoE) model, the feed-forward network (FFN) of each layer is replaced by E smaller FFNs, the experts, plus a tiny router that picks k of them for each token. The other E − k experts are skipped for that token.

# Dense FFN: every token uses all the weights
y = FFN(x)

# Sparse MoE FFN: the router picks k of E experts for THIS token
scores = router(x)                       # [E]   one score per expert
top    = topk(scores, k)                 # e.g. k = 8 of E = 256
y = Σ_shared FFN_s(x) + Σ_{i ∈ top} g_i · FFN_i(x)    # g_i = normalised score

That gives MoE two parameter counts, and they matter for different things:

  • Total parameters: everything that has to be stored. This sets the memory you need (and how many GPUs).
  • Active parameters: what one token actually touches. This sets FLOPs per token and, at small batch, the bytes read from memory per decoded token.
Why this is a big deal for inference. Decode is bound by memory bandwidth: each new token has to stream its weights from HBM/DRAM. A dense model reads all of its weights per token. An MoE reads only its active weights. DeepSeek-V3 stores 671B parameters but activates 37B per token, so at batch 1 its weight traffic per token is about that of a 37B dense model. The catch: all 671B must still be resident somewhere.

1. Dense FFN vs MoE FFN

Intuition. Same job, different staffing: a dense model has one generalist that every token must visit; an MoE has many narrower specialists and each token visits only k of them.

Only the FFN changes. Attention, norms, residuals and the LM head stay the same as in the transformer guide. Each expert is an ordinary SwiGLU FFN with its own weights, just narrower than a dense FFN would be.

What to notice: the router is just a d × E matrix and a top-k. All experts sit in memory, but each token runs only k of them (plus any shared expert), so FLOPs follow active parameters while memory follows total parameters.

  1. 1The router is a d × E matrix plus a top-k. Here E = 8 routed experts and top-k = 2, and the two winners get gates g = 0.7 and 0.3.
  2. 2The 6 idle experts are stored in memory but not run for this token: 8 + 1 experts stored, 2 + 1 run. A dense SwiGLU FFN (d → d_ff → d, 3·d·d_ff weights) is read in full by every token, so for it total = active.
  3. 3The shared expert has no routing and runs for every token. DeepSeek-V3, Kimi K2 and Qwen3.5 have one; Mixtral, Qwen3 and gpt-oss have none. Here y = shared(x) + 0.7·E1(x) + 0.3·E5(x).

Two practical facts follow from the shape of the network:

  • The experts are almost all of the weights. Counting from each config.json with moe.py, routed experts hold 97.4% of DeepSeek-V3's parameters, 96.6% of Qwen3-235B-A22B's and 98.2% of gpt-oss-120b's. Whatever you do to the experts (quantize, offload, shard) is what moves the memory needle.
  • Each expert is small. A DeepSeek-V3 expert is 3 × 7168 × 2048 ≈ 44M parameters, a Qwen3-30B-A3B expert only 4.7M. Small matrices per expert make GPU efficiency a kernel problem (see Section 5).

2. The Router

Intuition. The router is a scoring desk: one dot product per expert, keep the top k, turn their scores into weights that sum to 1.

The router is a linear layer W_r ∈ ℝ^{E×d} followed by a scoring function and a top-k. Three common variants:

What to notice: with softmax, renormalising over the chosen k gives exactly the same gates as a softmax over just those k logits, so the two orderings in different codebases are equivalent.

  1. 1The bias b only steers which experts are picked (auxiliary-loss-free balancing, §2.1). It never enters the gate values.
  2. 2Gates use the original scores s, renormalised over the k picked experts. DeepSeek-V3 then multiplies them by a routed scaling factor of 2.5.

Softmax → top-k → renormaliseQwen3, Mixtral (HF code)Identical to "top-k on logits, then softmax over those k", which gpt-oss uses
Sigmoid → (+ bias) top-k → normaliseDeepSeek-V3, Kimi K2, GLM-5Each expert is scored independently, so adding experts does not shrink scores

Top-k gating, step by step

Intuition. Score every expert, keep the k best, and mix their outputs in proportion to their scores.

g = softmax(top-k(Wr x))y = Σi ∈ top-k gi · Ei(x)
Read it aloud
"g is the softmax of the top-k router logits; y is the sum over the chosen experts of g-i times expert-i of x." x is one token's hidden vector [d]; Wr is the router matrix [E × d], so Wrx is E logits; top-k keeps the k largest; g holds k gates that sum to 1; each Ei is a SwiGLU FFN mapping [d] → [d], so y is [d].
Why it exists
Running every expert would cost E times the FLOPs. Top-k gives each token a few specialists and leaves the rest idle, so compute follows k, not E. The gates matter for learning too: the expert choice itself is discrete, so the router learns only through the gate values that scale each expert's output.
Tiny example

E = 4, k = 2, logits u = (2.0, 1.0, 0.5, −1.0):

softmax over all 4 = (0.609, 0.224, 0.136, 0.030) → top-2 = E0, E1

renormalise: g = (0.609, 0.224) / 0.833 = (0.731, 0.269) = softmax(2.0, 1.0)

E0(x) = (1, 0), E1(x) = (0, 2) → y = 0.731·(1, 0) + 0.269·(0, 2) = (0.731, 0.538)

A sigmoid router (DeepSeek-V3) scores σ(u) = (0.881, 0.731, 0.622, 0.269): same top-2, gates (0.546, 0.454).

Code
scores = (x @ W_r.T).softmax(-1)              # [T, E]
w, idx = scores.topk(k, dim=-1)                # [T, k]
w = w / w.sum(-1, keepdim=True)                # gates

2.1 Load balancing: why it is needed

Intuition. Without rules, everyone queues at the most popular desk. Balancing adds a small push toward spreading tokens evenly.

Left alone, a router collapses: a few experts win early, get more gradient, get better, win more. That wastes capacity in training and, at inference, overloads the GPUs that host the popular experts. Three fixes are in use:

MethodHow it worksUsed by
Auxiliary lossAdd α · E · Σᵢ fᵢ · Pᵢ to the loss. fᵢ is the fraction of tokens routed to expert i, Pᵢ is its mean router probability. It is minimised by a uniform spread. Switch Transformer used α = 10⁻².Switch Transformer; Qwen3 (computed over the global batch rather than per micro-batch)
Auxiliary-loss-free biasKeep a per-expert bias bᵢ that is added to the scores only for the top-k choice. After each step: overloaded expert → bᵢ −= γ, underloaded → bᵢ += γ. No extra gradient interferes with the language-model loss.DeepSeek-V3 (γ = 0.001, plus a tiny sequence-wise loss with α = 0.0001); DeepSeek-V4; Kimi K2 and GLM-5 configs use the same noaux_tc router
Capacity limitEach expert accepts at most C = ⌈capacity_factor · tokens · k / E⌉ tokens per batch; overflow is dropped (the residual carries the token through). Bounds the worst case but loses information.Switch Transformer (training). DeepSeek-V3 drops no tokens in training or inference.

The load-balancing loss, step by step

Intuition. Penalise the router when the experts that receive the most tokens are also the ones it is most confident about.

Laux = α · E · Σi fi · Pi
Read it aloud
"L-aux equals alpha times E times the sum over experts of f-i times P-i." fi is the fraction of routed slots that went to expert i (a count, no gradient); Pi is expert i's mean router probability over the batch (has a gradient); E is the number of experts; α is a small weight (Switch Transformer: 0.01).
Why it exists
Routers collapse: a popular expert gets more gradient, gets better, wins more tokens. fi·Pi is large when load and confidence pile up on the same experts: Laux = α when both are uniform and grows toward E·α as everything moves to one expert. The gradient flows through P, nudging probability away from overloaded experts. The aux-loss-free alternative skips the loss and adjusts a per-expert bias instead.
Tiny example

E = 2 experts:

collapsed: f = (1, 0), P = (0.9, 0.1) → 2·(1·0.9 + 0·0.1) = 1.8 → L = 1.8α

balanced: f = P = (0.5, 0.5) → 2·(0.25 + 0.25) = 1.0 → L = α (the minimum)

Aux-loss-free bias instead, E = 4, loads (6, 2, 4, 4), mean 4, γ = 0.001:

b += γ·sign(mean − load) = (−0.001, +0.001, 0, 0)

Code
f = load.float() / (T * k)                          # [E], no grad
P = (scores / scores.sum(-1, keepdim=True)).mean(0)  # [E]
aux = alpha * E * (f * P).sum()

2.3 Shared + fine-grained experts (DeepSeekMoE)

Intuition. More, smaller specialists give vastly more possible teams for the same cost; one always-present generalist handles the common stuff.

DeepSeekMoE made two changes to the Mixtral-style "few big experts" design, and nearly every large open MoE since has adopted at least the first:

  • Fine-grained experts: split each expert into m smaller ones and activate m times as many. FLOPs per token stay the same, but the number of possible expert combinations explodes, so experts can specialise more narrowly.
  • Shared experts: a few experts that every token uses. They absorb common knowledge (syntax, frequent patterns) so routed experts do not all have to relearn it.

What to notice: the fine-grained layout lights up more, smaller boxes. Mixtral picks 2 of 8 experts, C(8, 2) = 28 pairs, each expert 3 × 4096 × 14336 ≈ 176M parameters; DeepSeek-V3 picks 8 of 256, C(256, 8) ≈ 4.1 × 10¹⁴ sets, each expert 3 × 7168 × 2048 ≈ 44M parameters, and its always-on shared expert is the same size. For inference this means more, smaller GEMMs per layer, which is why grouped-GEMM kernels matter (Section 5.5). Qwen3 dropped the shared expert again, and Qwen3.5 brought one back, so the shared expert is a design choice rather than a rule.

3. The Full MoE Decoder Block

Intuition. Take the transformer from Module 1 and swap exactly one part: the FFN. Everything else stays.

Putting it together, an MoE LLM is the decoder-only transformer from Module 1 with two swaps: the FFN becomes an MoE FFN, and (in the DeepSeek lineage) attention becomes MLA. Some models keep their first layers dense (DeepSeek-V3 and GLM-5: 3, Kimi K2: 1); DeepSeek-V4 instead turns them into MoE layers that pick experts with a fixed hash of the token ID.

What to notice: nothing about attention changes when you add experts. MoE fixes the FFN half of the cost; the attention half (KV cache and context-length scaling) needs its own fix, which is where MLA comes in.

  1. 1Some models keep their first layers dense: DeepSeek-V3 has 3 dense layers with d_ff = 18,432 (GLM-5: 3, Kimi K2: 1). The embedding is 129,280 × 7168 in DeepSeek-V3.
  2. 2Attention is dense per token: every head, every layer, and it reads and writes the KV cache. Its cost grows with context, not with the number of experts. MLA in DeepSeek-V3 is 187M parameters per layer (§4). Each sub-block is pre-norm with a residual add (the ⊕ nodes).
  3. 3The MoE FFN: router → top-8 of 256 routed experts + 1 shared, each a SwiGLU 7168 → 2048 → 7168 (44M parameters). Routed experts hold 97.4% of all weights, but only 8 of 256 run per token.
  4. 4Where the bytes go at decode: at B = 1 about 36.6 GB of FP8 weights per token; at B = 128 almost every expert is touched, but the cost is shared by 128 tokens. The MTP head (training and speculative decoding) adds 14B parameters not counted in the 671B.

4. Multi-head Latent Attention: shrinking the KV cache

Intuition. Instead of storing every head's keys and values, store one compressed note per token and unzip it into per-head keys and values when needed.

MoE reduces the bytes of weights read per token. At long context or large batch, the other big byte stream is the KV cache: every decode step reads all cached keys and values of its sequence. The transformer guide covers the plain KV cache. Here are the four ways to size it, from biggest to smallest per token per layer:

GQA2 · n_kv · d_hgroups of query heads share one K/V headMixtral (8 KV), Qwen3 (4 KV), gpt-oss (8 KV)

What to notice: the cache holds only the red box. RoPE cannot be applied inside the compressed path (it would block folding W_UK into the query), so DeepSeek adds a small separate RoPE key k_R that is shared by all heads.

  1. 1Per token per layer the cache holds 512 + 64 = 576 values (DeepSeek-V3), instead of 2 × 128 heads × 128 dims = 32,768 for MHA. ht is 7168-wide; WDKV maps 7168 → 512 + 64.
  2. 2kR is a small RoPE key shared by all heads (the "decoupled RoPE"). It joins the scores directly: score = qC·kC + qR·kR, and out = softmax(score / √192)·v, then WO maps back to [7168].
  3. 3WUK and WUV rebuild per-head keys kC (128 heads × 128) and values v (128 × 128). At decode, qC·(WUKcKV) = (WUKᵀqC)·cKV, so WUK folds into the query and WUV into WO (the "absorbed" form): attention runs straight on the cache, 128 query heads sharing one 576-dim key, an MQA over the latent. The query path is compressed too: WDQ to cQ [1536], then WUQ to qC (128 × 128) and qR (128 × 64, RoPE).

The DeepSeek-V2 paper sizes this as (d_c + d_R) ≈ 4.5 · d_h per token per layer, "equal to GQA with only 2.25 groups", while reporting quality better than MHA. Computed for DeepSeek-V3's shape (61 layers, 128 heads, d_h = 128, BF16):

4.1 The catch: MLA trades bytes for FLOPs

In absorbed form, every one of the 128 query heads does a 576-dim dot product with every cached latent, then a 512-dim weighted sum. Counted with moe.py at 32K context, that is about 557 GFLOP per decoded token for DeepSeek-V3's attention, far more than the 73 GFLOP of all its active matmuls. Per byte of BF16 cache read, MLA does about 242 FLOPs; Qwen3-235B's GQA does 16, gpt-oss's 8 and Mixtral's 4. An H100 SXM (about 990 dense BF16 TFLOPS, 3.35 TB/s) breaks even at about 295 FLOP/byte, so MLA decode attention is close to compute-bound while GQA decode attention is firmly bandwidth-bound.

Where this went next (as of Oct 2026). DeepSeek-V3.2 keeps MLA but adds DeepSeek Sparse Attention: a cheap "lightning indexer" picks 2,048 cached tokens per query, and DSA runs on the MQA mode of MLA, so attention cost stops growing with context. DeepSeek-V4 (Apr 2026) goes further and compresses along the sequence axis: its CSA and HCA layers merge every m tokens into one shared key/value entry, reporting 10% of V3.2's KV cache at 1M tokens. Qwen3.5 instead makes 3 of every 4 layers Gated DeltaNet, a linear-attention recurrence with a fixed-size state, the same idea as Mamba. Three different routes to the same goal: fewer bytes per cached token.

5. Inference: why MoE decodes cheaply, and why it is still hard

Intuition. You pay rent for the whole team (all experts must sit in memory), but each token only pays wages to the k experts it uses (bytes read per token).

The general techniques used below (roofline estimates, batching, quantization, offloading, speculative decoding) are collected in the Memory & inference efficiency cookbook; this section applies them to MoE.

5.1 Decode reads active weights, but stores all of them

At batch 1, decoding one token is a chain of matrix-vector products: every weight is read once and used for 2 FLOPs. Arithmetic intensity is about 1 FLOP per byte at BF16, hundreds of times below the GPU's break-even point, so time per token ≈ bytes read ÷ memory bandwidth. For an MoE, bytes read ≈ active parameters × bytes per parameter. That gives an upper bound on tokens per second, independent of FLOPs:

tokens/s (batch 1)  ≤  memory bandwidth / (active params × bytes per param)
resident memory     ≥  total params × bytes per param   (+ KV cache + activations)

5.2 Batch size vs expert utilisation

The "read only active weights" argument holds for one token. A batch of B tokens in the same decode step each pick their own k experts. Under uniform routing, the expected number of distinct experts hit in a layer is

distinct(B) = E · (1 − (1 − k/E)^B)        # each expert is missed by one token with prob. 1 − k/E
# DeepSeek-V3 (E=256, k=8):  B=1 → 8,  B=8 → 57.4,  B=32 → 163.3,  B=128 → 251.6,  B=512 → 256.0

So by batch ~100 nearly every expert is read every step, and the step reads almost all 671B parameters. That is fine: the cost is now shared by B tokens. What matters for efficiency is tokens per expert = B·k/E. Each expert's weights are reused only that many times per read, so an MoE needs E/k times the batch of a dense model to reach the same arithmetic intensity. To get ~295 tokens per expert (the H100 break-even for BF16 and for FP8 alike), DeepSeek-V3 needs a global batch of about 295 × 256 / 8 ≈ 9,440 tokens per step. That is why large deployments spread experts over many GPUs and pool many users' requests (Section 5.3).

5.3 Expert parallelism and the all-to-all

Intuition. Each GPU hosts a subset of the specialists, so tokens have to travel to whichever GPU holds their expert, and the answers travel back.

A 671B model does not fit on one GPU, and slicing every small expert across GPUs (tensor parallelism) makes each GEMM tinier still. The standard answer is expert parallelism (EP): whole experts live on different GPUs, attention runs data-parallel, and two all-to-all exchanges per MoE layer move tokens to their experts and back.

What to notice: every token crosses the interconnect twice per MoE layer. Limiting how many devices a token may use bounds that traffic, and overlapping the all-to-all with compute hides it.

  1. 1Attention runs data-parallel: each GPU serves its own requests and computes the router for its own tokens (blue squares).
  2. 2Dispatch: each token is sent to the GPUs that own its k experts, one all-to-all exchange.
  3. 3Each GPU runs its 64 experts (EP = 4, 256 experts) as a grouped GEMM over the tokens it received from everyone (light squares).
  4. 4Combine: results go back to each token's home GPU (a second all-to-all), which forms y = Σ gi·Ei(x), adds the shared expert and moves on to the next layer (bottom row).

What production systems do about it:

  • Bound the fan-out. DeepSeek-V3 routes each token to experts on at most 4 nodes (node-limited routing), so cross-node traffic per token is capped no matter which 8 experts win.
  • Scale EP with the phase. DeepSeek-V3 serves prefill with 32-way EP and decode with 320-way EP: one expert per GPU, and 64 GPUs for redundant and shared experts.
  • Replicate hot experts. Routing is skewed in practice, so popular experts get redundant copies. vLLM's EPLB periodically rebalances which GPU holds which expert and supports redundant experts; its docs estimate about 2.4 GB of memory per redundant expert per EP rank for DeepSeek-V3.
  • Use dedicated kernels. DeepEP provides the dispatch/combine all-to-all (a high-throughput mode for prefill, a low-latency mode for decode, FP8 dispatch). vLLM sets EP size = TP × DP and selects these as all-to-all backends; TensorRT-LLM exposes TP, EP or a hybrid for MoE layers (moe_tp_size × moe_ep_size = tp_size).

5.4 Capacity factor and token dropping at inference

A capacity limit makes every expert's buffer a fixed size, which is convenient for static shapes. The cost is subtle: whether your token is dropped depends on which other tokens share the batch. moe.py shows it directly: with capacity factor 1.0, 12 of 60 tokens get a different output inside the batch than when run alone; dropless dispatch changes none. DeepSeek-V3 drops no tokens in training or inference, and dropless kernels (MegaBlocks) exist precisely so that nobody has to choose between dropping tokens and padding every expert to the worst case.

5.5 Grouped GEMM: from E tiny matmuls to one kernel

Intuition. Line the tokens up by expert so each expert works through one contiguous queue, then process all queues in one go.

The naive implementation loops over experts and launches E small GEMMs per layer, most of them nearly empty at decode. The fix is to permute tokens so that each expert's tokens are contiguous, then run one grouped GEMM that walks the segments:

Worked example (4 tokens, top-2 of 4 experts): the gates are t0: E1·0.6, E3·0.4; t1: E0·0.7, E2·0.3; t2: E1·0.5, E2·0.5; t3: E3·0.8, E1·0.2. Step 2 is argsort(expert_id) plus a gather of rows; segment offsets tell the kernel where each expert starts (1, 3, 2 and 2 rows). Step 4 scatters the rows back and sums: y0 = 0.6·E1 + 0.4·E3, y1 = 0.7·E0 + 0.3·E2, y2 = 0.5·E1 + 0.5·E2, y3 = 0.8·E3 + 0.2·E1.

What to notice: the permutation is cheap (an argsort and a gather); the win is that the expert math becomes one launch over contiguous memory. Prefill uses a contiguous layout; decode under CUDA graphs uses a masked layout with a fixed maximum per expert, because the CPU does not know the per-expert counts in advance (DeepGEMM documents both). moe.py's dispatch_sorted is the padded/masked flavour written with torch.bmm.

5.6 Quantizing the experts

Since routed experts are 91–99% of the weights in the models above, expert precision sets both the resident memory and the decode bytes. The common pattern is to quantize experts hardest and keep the small, sensitive parts in higher precision:

  • gpt-oss: MoE weights in MXFP4 (about 4.25 bits per parameter including block scales); attention, router, embeddings and LM head are left unconverted (modules_to_not_convert in its config). That is how 117B parameters fit in 60.8 GiB.
  • DeepSeek-V3: released in FP8 (E4M3) with one scale per 128 × 128 weight block; the Hugging Face implementation computes the router logits in FP32. A small error in router logits can flip which experts win, which is a discrete change, not a small perturbation.
  • DeepSeek-V4: expert weights in FP4 and most other weights in FP8, with quantization-aware training of the experts during post-training.

5.7 Edge: offloading and unified memory

On a single edge device the problem flips: batch is 1, so bandwidth per token is great (only k experts per layer), but total parameters must fit. When they do not, expert offloading keeps hot experts in fast memory and fetches the rest on demand. Eliseev & Mazur ran Mixtral-8x7B on consumer GPUs and free Colab this way, at about 2–3 tokens/s, using an LRU cache of experts per layer, speculative prefetch (apply the next layer's router to the current hidden state to guess its experts), and 2–3-bit expert quantization.

Jetson is different. On Jetson (Tegra) the CPU and the integrated GPU share the same SoC DRAM: "device memory, host memory, and unified memory are allocated on the same physical SoC DRAM" (CUDA for Tegra app note). "Offloading experts to CPU RAM" frees nothing there, and the next tier down is NVMe storage. On Orin and Thor the practical recipe is to choose an MoE whose quantized total fits in DRAM (Qwen3-30B-A3B at 4-bit is about 14 GiB, gpt-oss-120b is 60.7 GiB, which fits on a 128 GB Thor) and enjoy the small active set.

5.8 Multi-token prediction and speculative decoding (briefly)

DeepSeek-V3 trains one extra multi-token-prediction (MTP) module that predicts the token after next; at inference it can serve as a draft for speculative decoding. The paper reports an 85–90% acceptance rate for that second token and 1.8× tokens per second. DeepSeek-V4 keeps the same MTP setup, and Qwen3.5 also ships an MTP layer. One MoE-specific caveat follows from the formula in 5.2: verifying 2 tokens in one step is a batch of 2, so DeepSeek-V3 reads about 15.75 experts per layer instead of 8. Speculation saves fewer bytes on an MoE at batch 1 than on a dense model, where the second token's weights are free.

TopKRouter: scores, top-k, gates, aux loss and the aux-free bias ▼

Purpose: pick k experts per token and their gate weights. Note that bias is a buffer, not a parameter: no gradient flows into it, and it only enters the topk.

class TopKRouter(nn.Module):
    """
    scores  = sigmoid(x W_r^T)  or  softmax(x W_r^T)          [T, E]
    choice  = scores + bias     (bias only when balance == "aux_free")
    idx     = topk(choice, k)                                  [T, k]
    weights = scores[idx] / sum(scores[idx]) * routed_scaling  [T, k]

    The bias changes WHICH experts are picked, never the gate VALUE. That is the
    whole trick of auxiliary-loss-free balancing: no extra gradient touches the
    language-model loss.
    """

    def __init__(self, cfg: MoEConfig):
        super().__init__()
        self.E, self.k = cfg.n_routed_experts, cfg.top_k
        self.scoring, self.balance = cfg.scoring, cfg.balance
        self.aux_coef, self.gamma = cfg.aux_loss_coef, cfg.bias_update_speed
        self.scale = cfg.routed_scaling
        self.weight = nn.Parameter(torch.randn(self.E, cfg.d_model) * cfg.d_model ** -0.5)
        # Not a gradient parameter: updated by a rule, stored in the checkpoint.
        self.register_buffer("bias", torch.zeros(self.E))

    def forward(self, x: torch.Tensor):
        """x: [T, d] -> (idx [T,k], weights [T,k], aux_loss scalar, load [E])"""
        logits = x @ self.weight.t()                                  # [T, E]
        scores = logits.softmax(-1) if self.scoring == "softmax" else logits.sigmoid()
        choice = scores + self.bias if self.balance == "aux_free" else scores
        idx = choice.topk(self.k, dim=-1).indices                     # [T, k]
        w = scores.gather(-1, idx)
        w = w / w.sum(-1, keepdim=True) * self.scale                  # normalise over the k picked
        load = torch.bincount(idx.flatten(), minlength=self.E)        # tokens per expert

        aux = x.new_zeros(())
        if self.balance == "aux_loss" and self.training:
            # Switch-style: alpha * E * sum_i f_i * P_i
            #   f_i = fraction of routed slots that went to expert i (no gradient)
            #   P_i = mean normalised router probability of expert i (has gradient)
            T = x.shape[0]
            f = load.float() / (T * self.k)
            P = (scores / scores.sum(-1, keepdim=True)).mean(0)
            aux = self.aux_coef * self.E * (f * P).sum()               # = aux_coef when perfectly uniform
        return idx, w, aux, load

    @torch.no_grad()
    def update_bias(self, load: torch.Tensor):
        """Aux-loss-free balancing: raise the bias of under-loaded experts, lower over-loaded ones."""
        if self.balance != "aux_free":
            return
        err = load.float().mean() - load.float()                      # > 0 means under-loaded
        self.bias += self.gamma * err.sign()

Key insight: with perfectly uniform routing, fi = Pi = 1/E and the aux loss equals exactly aux_loss_coef. Anything above that value measures imbalance.

RoutedExperts: naive loop dispatch vs sort/scatter grouped dispatch ▼

Purpose: the same computation twice. The loop is easy to read; the sorted version is the shape real kernels use (one batched GEMM over a padded [E, C, d] buffer), and it is where a capacity limit naturally appears.

# ---- 2a. Naive: loop over experts ------------------------------------
def dispatch_loop(self, x: torch.Tensor, idx: torch.Tensor, w: torch.Tensor) -> torch.Tensor:
    """For each expert: find its tokens, run it, scatter-add the weighted result."""
    out = torch.zeros_like(x)
    for e in range(self.E):
        tok, slot = (idx == e).nonzero(as_tuple=True)              # which tokens chose e
        if tok.numel() == 0:
            continue                                               # an idle expert costs nothing
        out.index_add_(0, tok, self.expert(e, x[tok]) * w[tok, slot, None])
    return out

# ---- 2b. Grouped: sort by expert -> one batched GEMM -> unsort -------
def dispatch_sorted(self, x: torch.Tensor, idx: torch.Tensor, w: torch.Tensor,
                    capacity: Optional[int] = None) -> Tuple[torch.Tensor, int]:
    """
    1. flatten the T·k (token, expert) assignments and sort them by expert id
    2. copy tokens into a padded [E, C, d] buffer (C = capacity or max load)
    3. ONE batched matmul per weight matrix: [E, C, d] @ [E, d, f]
    4. scatter results back to token order, weighted by the gate
    If `capacity` is set, assignments beyond slot C of an expert are DROPPED
    (that token just gets less/no expert output, the residual carries it).
    Returns (output, n_dropped).
    """
    T, k = idx.shape
    flat_e = idx.flatten()                                         # [T·k]
    flat_tok = torch.arange(T, device=x.device).repeat_interleave(k)
    flat_w = w.flatten()
    order = torch.argsort(flat_e, stable=True)                     # group by expert
    e_sorted, tok_sorted, w_sorted = flat_e[order], flat_tok[order], flat_w[order]

    counts = torch.bincount(e_sorted, minlength=self.E)            # tokens per expert
    starts = torch.cumsum(counts, 0) - counts                      # segment offsets
    pos = torch.arange(T * k, device=x.device) - starts[e_sorted]  # slot within its expert

    C = int(counts.max()) if capacity is None else capacity
    keep = pos < C
    n_dropped = int((~keep).sum())
    e_k, pos_k, tok_k, w_k = e_sorted[keep], pos[keep], tok_sorted[keep], w_sorted[keep]

    buf = x.new_zeros(self.E, C, x.shape[-1])                      # padded "grouped" layout
    buf[e_k, pos_k] = x[tok_k]
    h = F.silu(torch.bmm(buf, self.w_gate)) * torch.bmm(buf, self.w_up)   # [E, C, f]
    y = torch.bmm(h, self.w_down)                                  # [E, C, d]

    out = torch.zeros_like(x)
    out.index_add_(0, tok_k, y[e_k, pos_k] * w_k[:, None])
    return out, n_dropped

Test: test_dispatch_equivalence() asserts torch.allclose(y_loop, y_sort, atol=1e-5) (max difference ≈ 3e-7) and shows that capacity 1.0 drops 23 of 240 assignments.

MLAttention: latent KV cache, naive and absorbed decode ▼

Purpose: cache only c_KV and k_R. The naive branch rebuilds per-head K and V; the absorbed branch folds W_UK into the query and W_UV into the output and never materialises them.

class MLAttention(nn.Module):
    """
    Per token we cache only:
        c_KV = RMSNorm(W_DKV x)          [d_c]    (content latent, shared by all heads)
        k_R  = RoPE(W_KR x)              [d_R]    (positional key, shared by all heads)
    Keys/values for head h are reconstructed on the fly:
        k_h = [W_UK_h c_KV ; k_R],   v_h = W_UV_h c_KV
    'absorbed' mode never builds k_h / v_h: it folds W_UK into the query and W_UV
    into the output, so attention runs against the d_c-dim latent directly.
    KV-cache elements per token per layer: d_c + d_R (vs 2·n_heads·d_h for MHA).
    """

    def __init__(self, cfg: MoEConfig):
        super().__init__()
        self.cfg = cfg
        d, nh = cfg.d_model, cfg.n_heads
        self.nh, self.dn, self.dr, self.dv, self.dc = nh, cfg.qk_nope_head_dim, cfg.qk_rope_head_dim, cfg.v_head_dim, cfg.kv_lora_rank
        # query path (low-rank, like DeepSeek-V3)
        self.w_dq = nn.Linear(d, cfg.q_lora_rank, bias=False)
        self.q_norm = RMSNorm(cfg.q_lora_rank)
        self.w_uq = nn.Linear(cfg.q_lora_rank, nh * (self.dn + self.dr), bias=False)
        # kv path: one down-projection produces [c_KV | k_R]
        self.w_dkv = nn.Linear(d, self.dc + self.dr, bias=False)
        self.kv_norm = RMSNorm(self.dc)
        self.w_uk = nn.Linear(self.dc, nh * self.dn, bias=False)
        self.w_uv = nn.Linear(self.dc, nh * self.dv, bias=False)
        self.w_o = nn.Linear(nh * self.dv, d, bias=False)
        self.scale = (self.dn + self.dr) ** -0.5
        self.absorbed = False

    def forward(self, x: torch.Tensor, cache: Optional[Dict[str, torch.Tensor]] = None, start_pos: int = 0):
        B, T, _ = x.shape
        pos = torch.arange(start_pos, start_pos + T)
        cos, sin = rope_cos_sin(pos, self.dr, self.cfg.rope_theta)

        q = self.w_uq(self.q_norm(self.w_dq(x))).view(B, T, self.nh, self.dn + self.dr)
        q_nope, q_rope = q.split([self.dn, self.dr], dim=-1)
        q_rope = apply_rope(q_rope.transpose(1, 2), cos, sin)               # [B, nh, T, dr]

        ckv, k_rope = self.w_dkv(x).split([self.dc, self.dr], dim=-1)
        ckv = self.kv_norm(ckv)                                             # [B, T, dc]
        k_rope = apply_rope(k_rope, cos, sin)                               # [B, T, dr]

        if cache is not None:                                               # append to latent cache
            if "ckv" in cache:
                ckv = torch.cat([cache["ckv"], ckv], dim=1)
                k_rope = torch.cat([cache["k_rope"], k_rope], dim=1)
            cache["ckv"], cache["k_rope"] = ckv, k_rope
        S = ckv.shape[1]                                                    # total keys

        # causal mask: query at absolute position start_pos+t sees keys 0..start_pos+t
        q_pos = torch.arange(start_pos, start_pos + T)[:, None]
        k_pos = torch.arange(S)[None, :]
        mask = k_pos > q_pos                                                # [T, S] True = blocked

        if not self.absorbed:
            # ---- naive: rebuild per-head K and V from the latent ----
            k_nope = self.w_uk(ckv).view(B, S, self.nh, self.dn).transpose(1, 2)    # [B, nh, S, dn]
            v = self.w_uv(ckv).view(B, S, self.nh, self.dv).transpose(1, 2)         # [B, nh, S, dv]
            scores = (q_nope.transpose(1, 2) @ k_nope.transpose(-1, -2)
                      + q_rope @ k_rope[:, None].transpose(-1, -2)) * self.scale    # [B, nh, T, S]
            attn = scores.masked_fill(mask, float("-inf")).softmax(-1)
            o = attn @ v                                                             # [B, nh, T, dv]
        else:
            # ---- absorbed: q_lat = q_nope · W_UK_h  (so q_nope·k_nope = q_lat·c_KV) ----
            W_uk = self.w_uk.weight.view(self.nh, self.dn, self.dc)
            W_uv = self.w_uv.weight.view(self.nh, self.dv, self.dc)
            q_lat = torch.einsum("bthn,hnc->bhtc", q_nope, W_uk)                     # [B, nh, T, dc]
            scores = (q_lat @ ckv[:, None].transpose(-1, -2)
                      + q_rope @ k_rope[:, None].transpose(-1, -2)) * self.scale     # [B, nh, T, S]
            attn = scores.masked_fill(mask, float("-inf")).softmax(-1)
            o_lat = attn @ ckv[:, None]                                              # [B, nh, T, dc]
            o = torch.einsum("bhtc,hvc->bhtv", o_lat, W_uv)                          # [B, nh, T, dv]
        o = o.transpose(1, 2).reshape(B, T, self.nh * self.dv)
        return self.w_o(o)

MoEBlock and TinyMoEDecoder: the full stack ▼

Purpose: pre-norm residual blocks, the first n_dense_layers with a dense FFN, the rest with the MoE FFN. The aux loss of every MoE layer is summed and returned with the logits.

class MoEBlock(nn.Module):
    def __init__(self, cfg: MoEConfig, dense: bool):
        super().__init__()
        self.attn_norm = RMSNorm(cfg.d_model)
        self.attn = MLAttention(cfg)
        self.ffn_norm = RMSNorm(cfg.d_model)
        self.dense = dense
        self.ffn = SwiGLU(cfg.d_model, cfg.d_ff_dense) if dense else MoEFFN(cfg)

    def forward(self, x, cache=None, start_pos=0):
        x = x + self.attn(self.attn_norm(x), cache, start_pos)
        if self.dense:
            return x + self.ffn(self.ffn_norm(x)), x.new_zeros(())
        y, aux = self.ffn(self.ffn_norm(x))
        return x + y, aux


class TinyMoEDecoder(nn.Module):
    def __init__(self, cfg: MoEConfig):
        super().__init__()
        self.cfg = cfg
        self.embed = nn.Embedding(cfg.vocab_size, cfg.d_model)
        self.blocks = nn.ModuleList([MoEBlock(cfg, dense=i < cfg.n_dense_layers) for i in range(cfg.n_layers)])
        self.norm = RMSNorm(cfg.d_model)
        self.lm_head = nn.Linear(cfg.d_model, cfg.vocab_size, bias=False)

    def forward(self, ids: torch.Tensor, caches: Optional[List[dict]] = None, start_pos: int = 0):
        x = self.embed(ids)
        aux_total = x.new_zeros(())
        for i, blk in enumerate(self.blocks):
            x, aux = blk(x, None if caches is None else caches[i], start_pos)
            aux_total = aux_total + aux
        return self.lm_head(self.norm(x)), aux_total
The analytic model behind every number in this guide ▼

Purpose: parameter counts, distinct experts and bytes per decode step from a config. test_param_formula() checks analyze() against the real module's parameter count, and the calculator below runs the same formulas in JavaScript.

def analyze(spec: dict) -> dict:
    d, L, m = spec["d"], spec["L"], spec["moe"]
    E, k, S, f = m["E"], m["k"], m["shared"], m["d_expert"]
    expert = 3 * d * f + ((2 * f + d) if m.get("expert_bias") else 0)
    router = E * d + (E if m.get("router_bias") else 0)
    n_moe = L - spec["n_dense"]
    emb = spec["vocab"] * d
    head = 0 if spec["tied"] else spec["vocab"] * d
    common = emb + head + d + L * (attn_params(d, spec["attn"]) + 2 * d) + spec["n_dense"] * 3 * d * spec["d_ff_dense"]
    total = common + n_moe * (E * expert + S * 3 * d * f + router)
    active = common + n_moe * (k * expert + S * 3 * d * f + router)
    return dict(total=total, active=active, active_noemb=active - emb, expert=expert, n_moe=n_moe, E=E, k=k,
                kv_per_tok=kv_elems_per_token(spec))


def distinct_experts(E: int, k: int, B: int) -> float:
    """Expected number of distinct experts hit in one layer by B tokens, each picking k of E uniformly."""
    return E * (1.0 - (1.0 - k / E) ** B)


def weight_bytes(spec: dict, w_bytes: float, expert_bytes: Optional[float] = None) -> float:
    """Resident weight memory. Routed experts may use their own precision (gpt-oss: MXFP4 = 4.25 bits)."""
    r = analyze(spec)
    eb = w_bytes if expert_bytes is None else expert_bytes
    routed = r["n_moe"] * r["E"] * r["expert"]
    return (r["total"] - routed) * w_bytes + routed * eb


def decode_bytes_per_step(spec: dict, B: int, ctx: int, w_bytes: float, kv_bytes: float,
                          expert_bytes: Optional[float] = None) -> dict:
    """Bytes read from memory for ONE decode step of a batch of B sequences, each with `ctx` cached tokens."""
    r = analyze(spec)
    eb = w_bytes if expert_bytes is None else expert_bytes
    always = r["active_noemb"] - r["n_moe"] * r["k"] * r["expert"]       # attention, shared, dense, head, router
    dx = distinct_experts(r["E"], r["k"], B)
    weights = always * w_bytes + r["n_moe"] * dx * r["expert"] * eb
    kv = B * ctx * kv_elems_per_token(spec, ctx) * kv_bytes
    return dict(distinct=dx, weights=weights, kv=kv, total=weights + kv, per_token=(weights + kv) / B)

9. Connection to the Rest of the Roadmap

  • Back to Transformer: MoE changes only the FFN; the attention, KV cache and FlashAttention material all still apply, and MLA is a drop-in replacement for the attention block.
  • Back to Mamba: MoE cuts the FFN bytes, Mamba cuts the context bytes. Qwen3.5 combines both: a 512-expert MoE FFN in every layer, with Gated DeltaNet recurrent layers for 3 of every 4 mixers.
  • VLMs: the language half of a VLM is increasingly an MoE: Qwen3.5-397B-A17B ships with a vision encoder in the same checkpoint. Everything here about resident memory and expert parallelism carries over.
  • Next, BEV Perception: back to dense vision models, where batch is fixed by the camera rig and latency budgets are hard. Keep the roofline habit: bytes per frame ÷ bandwidth.

Key Takeaways

  • An MoE stores E experts per layer but runs k of them per token: memory follows total parameters, FLOPs and batch-1 decode bytes follow active parameters.
  • The router is a d × E linear layer plus top-k; softmax-then-renormalise and top-k-then-softmax give identical gates.
  • Load balancing is essential: an auxiliary loss, or DeepSeek-V3's bias that changes which experts win but never the gate value.
  • Fine-grained experts, often plus a shared expert (DeepSeekMoE), is the dominant 2025–2026 recipe: 128–512 small experts, with 3–5% of the weights active in the largest models.
  • MLA caches a 576-value latent per token per layer in DeepSeek-V3 instead of 32,768 MHA values, at the cost of more decode FLOPs.
  • Batch kills the "only k experts" advantage per step (DeepSeek-V3 touches ~163 of 256 experts at batch 32) but amortises it per token; experts need about E/k times a dense model's batch to be compute-bound.
  • Serving at scale is expert parallelism + all-to-all + grouped GEMMs + replicated hot experts; on the edge it is "quantize the experts until the total fits".

Self-Check

1. At batch 1, why can DeepSeek-V3 (671B total) decode faster than a 70B dense model on the same hardware, assuming both fit?

Answer

Batch-1 decode is memory-bandwidth-bound, so time per token ≈ bytes of weights read ÷ bandwidth. DeepSeek-V3 reads only its ~37B active parameters per token; the dense model reads all 70B. Same precision means roughly half the bytes, so roughly twice the token rate ceiling. Total parameters only set how much memory you need.

2. DeepSeek-V3 has 61 layers, d_c = 512 and d_R = 64. How big is its MLA KV cache per token at BF16, and for one 128K-token sequence?

Answer

61 × (512 + 64) × 2 B = 70,272 B ≈ 68.6 KiB per token. × 131,072 tokens ≈ 8.58 GiB. With full MHA (128 heads × 128 dims for K and V) it would be 3,904 KiB per token and 488 GiB, 56.9× more.

3. Qwen3-235B-A22B uses GQA with 4 KV heads of dim 128 in 94 layers. What is its BF16 KV cache for one 32K-token sequence?

Answer

Per token: 94 × 2 × 4 × 128 × 2 B = 192,512 B (188 KiB). × 32,768 = 6,308,233,216 B ≈ 5.88 GiB, about 2.7× DeepSeek-V3's MLA cache at the same length (2.14 GiB), despite having only 4 KV heads.

4. With uniform routing, how many of DeepSeek-V3's 256 experts per layer does a decode batch of 32 tokens touch?

Answer

256 × (1 − (1 − 8/256)32) ≈ 163.3. A batch of 32 already reads about 64% of the expert weights each step, which is why batching erodes the "read only active weights" advantage per step while still lowering bytes per token.

5. In auxiliary-loss-free balancing, the bias is added to the scores only for the top-k choice, not to the gate weights. Why?

Answer

The bias is a control signal for load, not a statement about how useful an expert is for this token. If it entered the gate values, it would change the model's output in a way the language-model loss never asked for and would leak load-balancing pressure into the function being learned, which is exactly the interference an auxiliary loss causes. Keeping it in the selection only changes which experts get the token.

6. A training batch has 4,096 tokens, 64 experts, top-8 and capacity factor 1.25. What is the per-expert capacity, and what happens if one expert receives 700 assignments?

Answer

C = ⌈1.25 × 4096 × 8 / 64⌉ = 640 slots. The 60 assignments over capacity are dropped: those tokens get no contribution from that expert and pass through on the residual path. Under dropless routing the expert would instead process all 700.

7. Roughly what global decode batch does DeepSeek-V3 need before its experts become compute-bound on an H100, and why is it so much larger than for a dense model?

Answer

An H100 SXM breaks even at about 990 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/byte, i.e. about 295 tokens per weight read at BF16 (or FP8 weights with FP8 math). Each expert sees only B·k/E of the batch, so B ≈ 295 × 256 / 8 ≈ 9,440 tokens. A dense model reaches that intensity at B ≈ 295. Hence large expert-parallel deployments that pool many users per step.

8. Qwen3-30B-A3B is quantized to 4 bits and run on a Jetson AGX Orin 64GB (204.8 GB/s). What is the batch-1 token-rate ceiling, and how does it compare with a dense 30B at 4 bits?

Answer

Active weights excluding the embedding lookup are ≈ 3.04B → 1.52 GB per token → ≤ 135 tok/s. A dense 30B reads ≈ 15.1 GB per token → ≤ 13.6 tok/s. Both need ≈ 14.2 GiB resident, which fits in 64 GB of shared DRAM.

9. Why is MLA's decode attention much closer to compute-bound than GQA's?

Answer

In absorbed form all 128 query heads attend to the same 576-value latent per cached token, so each byte of cache read feeds many heads: ≈ 242 FLOPs per BF16 byte for DeepSeek-V3. In Qwen3-235B's GQA each KV head serves only 16 query heads (≈ 16 FLOP/byte). MLA reads fewer bytes but does more math per byte.

10. Speculative decoding verifies 2 tokens per step. Why does that save less on DeepSeek-V3 at batch 1 than on a dense model?

Answer

A dense model reads the same weights whether it verifies 1 or 2 tokens, so the second token is nearly free. In an MoE the two tokens usually pick different experts: expected distinct experts per layer go from 8 to 256 × (1 − (31/32)²) ≈ 15.75, almost doubling the expert bytes for that step.

Hands-on Exercises

Build it yourself. Start with the guided lab labs/lab08_moe_router.py: implement the softmax and sigmoid top-k routers, the load-balancing loss, per-expert-loop and sort-and-scatter dispatch, and capacity-limited dispatch with token dropping. Check each step with python labs/check.py 8, then do the exercises below.

All exercises use moe.py. Import it with from moe import * from the moe/ directory.

1. A Mixtral-shaped toy easy

Build MoEConfig(n_routed_experts=8, top_k=2, n_shared_experts=0, scoring="softmax", balance="aux_loss") and a TinyMoEDecoder from it. Print total and active parameters. Verify: assert count_parameters(model) == analyze(spec_from_config(cfg))["total"], and run test_dispatch_equivalence-style loop vs sorted outputs for this config.

2. The aux loss floor easy

Create a TopKRouter with balance="aux_loss", zero its weight, put it in training mode and route 100 random tokens. Verify: abs(aux.item() - cfg.aux_loss_coef) < 1e-6. Then explain why the result does not depend on which experts the ties sent tokens to (hint: look at Pi).

3. Capacity factor sweep medium

For capacity factors 0.75, 1.0, 1.25, 1.5 and 2.0, route 512 random tokens through an MoEFFN and record moe.last_dropped / (512 * k). Verify: the dropped fraction is non-increasing in the capacity factor, and with capacity_factor=None, moe.last_dropped == 0.

4. Group-limited routing medium

Add DeepSeek-V3-style group-limited routing to TopKRouter: split E experts into G groups, score each group by the sum of its top-2 scores, keep the best M groups, then take top-k inside them (the HF config calls these n_group and topk_group). Verify: assert all(len(set((row // (E // G)).tolist())) <= M for row in idx), and that with M = G the routing equals the original.

5. INT8 experts hard

Quantize w_gate, w_up and w_down to symmetric INT8 with one scale per output channel per expert, dequantize, and rerun the MoE FFN. Verify: relative error (y_q - y).norm() / y.norm() < 2e-2, and report how many bytes the routed experts take before and after. Then quantize the router weight the same way and count how many tokens change their top-k set.

6. Simulate expert offloading hard

Decode 200 tokens with the tiny model and record each MoE layer's chosen experts per step. Simulate a per-layer LRU cache holding C experts and count misses for C = 1, 2, 4, 8, 16. Verify: with C = E the only misses are first uses (misses == number of distinct experts ever used), and the miss rate is non-increasing in C. Bonus: add "speculative prefetch" by running layer l+1's router on layer l's output and measure the hit rate of that guess.
