The Core Idea: One Model, Many Robots

A robot foundation model is a single pretrained network that can drive different robots, with different joints, action spaces and sensors. "Foundation" means it is pretrained on large cross-embodiment data and then post-trained for a specific robot or task, instead of being trained from scratch per robot.

The key insight: most of what a robot needs is embodiment-agnostic — what objects look like, what "put the cup on the table" means, roughly how things move. Only the last step, "which motors do I command, and how is my body's state encoded?", is embodiment-specific. Sharing the large VLM and DiT across robots while keeping thin per-robot input/output layers is what makes cross-embodiment data useful.

1. The Dual-System Architecture

A human driver does not re-plan "I'm driving home" at every steering correction. Slow, deliberate reasoning ("System 2") and fast, reflexive control ("System 1") run at different rates. GR00T borrows that vocabulary: the VLM interprets the scene and the instruction, and the action head turns that into motor commands. The paper quotes 10 Hz for the VLM and 120 Hz for motor actions.

  • System 2 runs once per chunk. It processes the camera images and the instruction. Robot state does not go in here: in GR00T the state enters System 1. In N1-2B the VLM is 1.34B of the 2.2B parameters.
  • System 1 runs K = 4 times per chunk. It is a DiT over [state token, 16 action tokens] that cross-attends to the cached System 2 tokens. Each pass is cheap because it skips all vision and language processing.

Without the split, every denoising step would re-run the VLM. In the toy rfm_base (2 cameras, 4 steps) that is 3.1× more FLOPs per chunk for an identical result (see the calculator).

Synchronous: observe → infer (robot waits) → execute e actions → repeat. Asynchronous: start a new inference every max(e/f, L) and switch to the new chunk when it lands, skipping the actions whose time has already passed. Asynchronous never waits as long as H/f ≥ period + L, but actions are always based on an observation at least L old. Real-time chunking adds smoothing at the switch: it freezes the actions that execute during inference and inpaints the rest. Presets: π0 executes 25 of 50 actions on 50 Hz robots, 73 ms on an RTX 4090; GR00T N1: 120 Hz, H = 16, 63.9 ms on an L40 (e = 12 is one 10 Hz cycle). The what-if row uses GR00T N1.7's measured 312 ms on a Jetson Orin at 30 W with N1.7's H = 40, at N1's 120 Hz.

2. Full Model Pipeline

Three things to notice:

  • System 2 → System 1 is cross-attention, to a middle layer. The DiT's even blocks attend to the cached VL tokens, and its odd blocks let the state and action tokens talk to each other. Contrast π0, where the action expert shares attention with the VLM at every layer (previous module).
  • Per-embodiment routing is thin. In rfm_base one robot's encoders and decoder are 362,016 parameters, about 2% of the ~18.5M shared transformer weights.
  • Timestep conditioning is adaptive LayerNorm, as in the diffusion module's DiT, but GR00T's variant is scale + shift on each attention block's input norm, with no residual gate (no "-Zero"). The embodiment does not enter the AdaLN condition: it is handled by the per-robot encoders and decoder.

3. Heterogeneous I/O — How Multi-Embodiment Routing Works

Robots have different state and action sizes. Two ingredients make one network handle all of them: padding (every state is zero-padded to a maximum width, every action chunk too, and the loss ignores the padded dimensions) and embodiment-specific weights for the layers that touch those raw vectors.

Why not a ModuleDict keyed by robot name? It is the most readable version, and fine when every batch holds a single robot. With mixed batches you would split the batch per robot, run several small matmuls and stitch the results back together. The gathered-tensor version does it in one shot. It is what Isaac-GR00T's CategorySpecificLinear implements.

4. Training on Cross-Embodiment Data

# One training step on a mixed batch (robot_fm.RobotFoundationModel.compute_loss)
vl = model.encode_system2(batch["images"], batch["token_ids"])   # no state here
t = 0.999 * (1 - Beta(1.5, 1).sample((B,)))                   # noisy end favoured
noise = torch.randn_like(a)                                         # a: [B, 16, 32] padded
x_t = (1 - t) * noise + t * a
v_pred = model.system1(x_t, t, batch["state"], vl, batch["embodiment_id"])
mask = action_mask(batch["embodiment_id"], H)                       # 1 on real dims only
loss = (((v_pred - (a - noise)) ** 2) * mask).sum() / mask.sum()
loss.backward()

5. Code Walkthrough

CategorySpecificLinear and the action encoder ▼ 
class CategorySpecificLinear(nn.Module):
    def __init__(self, num_categories, in_dim, out_dim):
        self.W = nn.Parameter(0.02 * torch.randn(num_categories, in_dim, out_dim))
        self.b = nn.Parameter(torch.zeros(num_categories, out_dim))

    def forward(self, x, cat_ids):                  # x [B, T, in], cat_ids [B]
        return torch.bmm(x, self.W[cat_ids]) + self.b[cat_ids].unsqueeze(1)

class MultiEmbodimentActionEncoder(nn.Module):        # W1, W2, W3 are all per-robot
    def forward(self, actions, t_bucket, cat_ids):
        tau = sinusoidal(t_bucket, self.hidden)                 # flow time, one per sample
        x = torch.cat([self.W1(actions, cat_ids), tau], dim=-1)
        return self.W3(F.silu(self.W2(x, cat_ids)), cat_ids)
System1ActionHead.forward — alternating cross/self attention with AdaLN ▼ 
def forward(self, x_t, t, state, vl_tokens, emb_ids):
    t_bucket = (t * 1000).long()                                  # GR00T discretises t
    s = self.state_encoder(state[:, None], emb_ids)                 # [B, 1, d]  per-robot
    a = self.action_encoder(x_t, t_bucket, emb_ids) + self.pos_embed.weight[None]
    h = torch.cat([s, a], dim=1)                                    # [B, 1 + H, d]
    temb = self.time_mlp(sinusoidal(t_bucket, self.d))
    for blk in self.blocks:                                         # even: cross-attn, odd: self-attn
        h = blk(h, temb, vl_tokens)
    shift, scale = self.proj_out_1(F.silu(temb)).chunk(2, dim=-1)
    h = self.proj_out_2(self.norm_out(h) * (1 + scale[:, None]) + shift[:, None])
    return self.action_decoder(h, emb_ids)[:, -self.horizon:]          # per-robot decoder

class DiTBlock(nn.Module):
    def forward(self, x, temb, ctx=None):
        h = self.norm1(x, temb)                       # norm(x) * (1 + scale(t)) + shift(t)
        kv = ctx if self.is_cross else h
        x = x + self.attn(h, kv, kv)[0]
        return x + self.ff(self.norm3(x))
generate_action — System 2 once, System 1 four times ▼ 
@torch.no_grad()
def generate_action(self, images, token_ids, state, embodiment_ids, n_steps=4, vl_tokens=None):
    if vl_tokens is None:
        vl_tokens = self.encode_system2(images, token_ids)            # System 2: once
    x = torch.randn(B, self.horizon, MAX_ACTION_DIM)                  # t = 0: noise
    dt = 1.0 / n_steps
    for i in range(n_steps):                                          # System 1: 4 times
        t = torch.full((B,), i * dt)
        x = x + self.system1(x, t, state, vl_tokens, embodiment_ids) * dt
    return x                                                          # padded; model.unpad(x, name)

7. Critical Optimizations

7.1 Run System 2 once per chunk ▼

Foundational. The VL tokens do not depend on the noisy actions, so re-running the VLM at each of the K denoising steps would recompute the same tensor K times. In rfm_base that would be 3.1× the FLOPs per chunk; with a real 1B+ VLM and a smaller head, the ratio approaches K.

7.2 Cache the cross-attention K/V of the VL tokens ▼

Inside one chunk the VL tokens are fixed, so each cross-attention block's keys and values (Wk·VL, Wv·VL) are identical across the K steps. Compute them once:

kv_cache = [(blk.Wk(vl), blk.Wv(vl)) for blk in cross_blocks]    # once per chunk
for i in range(K):
    x = system1_step(x, t_i, kv_cache)                                  # reuse

How much it saves depends on shapes: with 140 VL tokens against 17 action-side tokens, the K/V projections are 46% of a System 1 step in rfm_base (the calculator shows this share for your settings). Note that nn.MultiheadAttention does not expose this; you need a custom attention module, which is one more reason deployments export to TensorRT.

7.3 Mixed-embodiment batches without kernel-launch overhead ▼

With per-robot nn.Modules, a mixed batch means a loop: split the batch by robot, launch small matmuls per group, scatter back. Stacking the per-robot weights into one tensor and gathering per sample (Section 3) keeps it to one batched matmul per layer. That makes it cheap to shuffle robots freely within a batch, which also keeps each gradient step representative of the whole data mixture.

7.4 What to freeze — and how GR00T's choice changed across versions ▼
  • N1: the language part of the VLM is frozen in pre-training and post-training; the vision encoder and the DiT are trained.
  • N1.5: the whole VLM stays frozen in both pre-training and fine-tuning (README: "preserving language understanding and improving generalization").
  • N1.6: unfreezes the top 4 VLM layers during pre-training (replacing N1.5's 4-layer adapter after the VLM).
  • N1.7 (model-config defaults): tune_llm = False, tune_visual = False; the projector, the DiT and the VL LayerNorm are tuned.

Freezing saves the optimizer state and gradients for most of the parameters and protects the VLM's general knowledge. The price is less adaptation of the visual features to robot data. Compare π0 (trains everything) and knowledge insulation (VLA module, 6.2).

7.5 Quantization and TensorRT: measured numbers ▼

Isaac-GR00T's deployment guide exports the whole N1.7 pipeline (vision, LLM, state/action encoders, DiT, decoder) to TensorRT. On AGX Thor (120 W) a full policy call drops from 111.5 ms (PyTorch eager) to 77.6 ms (TensorRT) and 35.9 ms (TensorRT + mixed NVFP4). All TensorRT rows passed NVIDIA's 0.99 cosine-similarity check on the final actions. That check is not a closed-loop success test, so re-validate on the robot. Section 8 has the full table.

9. As of Oct 2026: GR00T N1 → N1.7

The GR00T N1 paper (Mar 2025) describes the architecture taught here. The open releases since (Isaac-GR00T READMEs):
  • N1.5: frozen VLM, upgraded to Eagle 2.5 with better grounding; adds the FLARE objective (future latent representation alignment) next to flow matching, to learn from human egocentric video; the README reports language following on GR-1 tasks rising from 46.6% to 93.3%.
  • N1.6: Cosmos-Reason-2B VLM variant with native-aspect-ratio images; a 2× larger DiT (32 vs 16 layers); top 4 VLM layers unfrozen during pre-training; predicts state-relative action chunks for most embodiments.
  • N1.7 (current GA release, Apache 2.0): Cosmos-Reason2-2B backbone (Qwen3-VL architecture), still reading layer 12; a relative end-effector action space shared by robots and humans, which enables pre-training on 20K hours of EgoScale human video; state/action padded to 132 dims; action horizon 40; full TensorRT export (Section 8).
  • Around it: Physical Intelligence's π0.5 → π0.6 / π*0.6 (RL from experience) → π0.7 (steerable prompts), and Google DeepMind's Gemini Robotics 2 family, which pairs a VLA with an embodied-reasoning model and includes an on-device variant. See the VLA module's update box for links.

10. Open Research Questions

This module ends with open problems. The field moves fast, so treat these as live questions:

  1. Scaling. Do more data and parameters improve robot policies as predictably as they improve LLMs? Robot data is still orders of magnitude smaller than web text, and evaluation is expensive (real robots, real time).
  2. Data beyond teleoperation. Human video (GR00T N1.7's 20K hours of EgoScale; Physical Intelligence's Dec 2025 "Emergence of Human to Robot Transfer in VLAs"), simulation and synthetic data. The open question is how much each transfers, and through which shared action representation.
  3. Learning from experience. Imitation caps you at demonstrator quality. π*0.6's Recap shows one route (value function + advantage conditioning). Standard policy gradients do not drop straight into flow-matching policies, which lack a cheap exact log-likelihood.
  4. Reacting mid-chunk. Chunks run open loop between calls. Real-time chunking and asynchronous inference reduce the problem but do not eliminate the latency between seeing and acting.
  5. Cross-morphology transfer. What transfers from arms to humanoids, and what (balance, contact-rich control) needs robot-specific data or a separate low-level controller?
  6. Sim-to-real. Simulation is cheap but differs from reality in rendering and physics; closing the gap remains an active effort.

11. Closing the Roadmap

This is the last module of the main path. Looking back:

  • Transformer: attention, the KV cache, everything else builds on it
  • ViT: images as patch tokens
  • VLM: image tokens inside a language model
  • Diffusion (DiT): iterative denoising with timestep-conditioned LayerNorm
  • Mamba: state-space models with constant-memory inference
  • Mixture-of-Experts LLMs: routing tokens to different weights
  • BEV: multi-camera geometry and deformable attention
  • VLA: a VLM plus an action expert, flow matching, action chunks
  • Robot foundation models: dual-rate systems and per-embodiment I/O

The robot foundation model reuses almost every earlier block: transformer attention (both systems), ViT patches (vision encoder), VLM fusion (System 2), DiT-style adaptive normalization (System 1), flow matching and action chunks (VLA), and routing by ID (a cousin of MoE routing, decided by the robot rather than learned per token). BEV and Mamba are the parallel tracks: BEV-style geometry matters when many cameras must agree on metric space, and state-space models are one answer to long observation histories.

Key Takeaways

  • System 2 (a VLM on images + text) runs once per chunk; System 1 (a DiT) runs K = 4 flow-matching steps on [state, actions] and cross-attends to the cached VLM tokens.
  • GR00T reads a middle LLM layer (the 12th) and drops the layers above it, which the paper reports is faster and better.
  • Robot state goes into System 1, not the VLM.
  • Per-robot state encoder, action encoder and action decoder; everything else is shared (92.7% shared in the toy rfm_base with 4 robots).
  • Gathered weight tensors (CategorySpecificLinear) plus padding and masked losses let one batch mix robots with one kernel per layer.
  • Real-time control is a budget: with synchronous execution the robot waits L every call; asynchronous execution needs H/f ≥ period + L.
  • As of Oct 2026, GR00T N1.7 runs a full call in 35.9 ms on Jetson AGX Thor with TensorRT + NVFP4 and pre-trains on human video via a shared relative end-effector action space.

Self-Check

1. Why does GR00T put the robot state into System 1 rather than into the VLM prompt?

Answer

The state is low-dimensional, robot-specific and changes fast. It needs a per-robot encoder, and the action head is where per-robot layers live. The VLM then sees only images and language, which are shared across robots. (π0 also routes state to its action expert, as a separate token block.)

2. At the paper's rates (VLM 10 Hz, actions 120 Hz, H = 16), how many actions does one chunk hold, and how long does it last?

Answer

16 actions at 120 Hz last 16 / 120 = 133 ms, a little longer than the 100 ms between VLM updates (12 actions). Whether that is enough also depends on latency: a chunk computed from an observation at time s only arrives at s + L. In the timeline widget, asynchronous execution with L = 63.9 ms needs H ≥ 20 to never run dry.

3. In rfm_base, how many parameters does one robot add, and why is that cheap?

Answer

362,016 (state encoder 82,432 + action encoder 205,568 + decoder 74,016). That is about 2% of the ~18.5M shared transformer weights, because the per-robot layers only touch the small raw state/action vectors and the 256-wide token stream.

4. A batch has robot IDs [0, 2, 1, 0]. What does W[cat_ids] produce, and why is that better than looping over a ModuleDict?

Answer

A [4, in, out] tensor holding W[0], W[2], W[1], W[0], which feeds one torch.bmm. A ModuleDict needs a Python loop or per-robot sub-batches, i.e. several small kernel launches plus gather/scatter. The tensor version also makes "add a robot" a matter of filling a spare slot.

5. Synchronous execution, f = 50 Hz, e = 25 executed actions per call, L = 73 ms. What fraction of time does the robot stand still, and how many actions per second does it execute?

Answer

Cycle = L + e/f = 73 + 500 = 573 ms, idle 73 ms → 12.7% standing still; 25 actions per 573 ms ≈ 43.6 actions/s instead of 50.

6. Asynchronous execution with L = 312 ms, f = 120 Hz, H = 40, e = 12. Can the robot avoid pausing? What would fix it?

Answer

The re-plan period is max(e/f, L) = max(100, 312) = 312 ms, and the chunk covers 40/120 = 333 ms. A chunk must cover period + L = 624 ms, so the robot runs dry for about 291 ms per cycle. Fixes: faster inference (TensorRT/NVFP4, a bigger module), a longer horizon, or a lower control rate (at 60 Hz, 40 actions cover 667 ms ≥ 624 ms).

7. Why can the K/V projections of the VL tokens be cached across denoising steps, but not the queries?

Answer

K and V come from the VL tokens, which are fixed for the chunk. The queries come from the state + noisy action tokens, which change at every step.

8. GR00T's DiT uses adaptive LayerNorm conditioned on the timestep. What does the conditioning not include, and where does that information enter instead?

Answer

The embodiment. Robot identity enters through the per-robot state encoder, action encoder (which also sees t) and action decoder, not through the shared AdaLN.

Hands-On Exercises

Run from the robot-fm/ folder; CPU is fine.

1. Routing equals separate layers

Build a CategorySpecificLinear(5, 7, 3) and a random batch with IDs [0, 3, 3, 1, 4, 0]. For each sample, check the output equals x[i] @ W[id] + b[id].

assert torch.allclose(y[i], x[i] @ csl.W[ids[i]] + csl.b[ids[i]], atol=1e-6)

2. Mixed batch == per-sample runs

With make_batch(list(EMBODIMENTS), 16), run model.system1 on the full batch and on each sample alone (same x_t, t). Assert the outputs match, which proves no information leaks between robots in a batch.

3. Count what one robot costs

Check per_embodiment_params(256) == 362016 and that rfm_cost()["params_dit"] equals the System 1 parameters minus the per-robot modules for rfm_base(). Then add a fifth robot to EMBODIMENTS (it fits into a spare slot) and confirm the parameter count does not change.

4. Cache the cross-attention K/V

Write a small cross-attention module with explicit Wq, Wk, Wv, Wo and a precompute_kv(vl) method. Verify the cached path equals the uncached one with torch.allclose, then time 4 denoising steps both ways with 512 VL tokens.

5. Simulate the budget

Re-implement the timeline widget's synchronous and asynchronous models in Python. Reproduce self-check 5 (12.7% idle) and 6 (≈ 291 ms dry per cycle). Then find the smallest horizon H that removes all pauses at f = 120 Hz with L = 35.9 ms and e = 12.
